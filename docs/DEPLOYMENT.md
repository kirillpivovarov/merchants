# Развёртывание и эксплуатация

## Node.js: основной сервер

```bash
npm ci
npm run build
AUTH_TOKEN='replace-with-a-long-random-secret' HOST=0.0.0.0 npm start
```

Не используйте пример секрета буквально. Введите собственное значение через менеджер секретов сервера. Для разработки на localhost можно не задавать AUTH_TOKEN.

Переменные:

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| PORT | 3000 | HTTP-порт |
| HOST | 127.0.0.1 | Интерфейс; внешний без ключа запрещён |
| DB_PATH | data/meridian.sqlite | Постоянный путь SQLite |
| AUTH_TOKEN | отсутствует | Ключ входа; хранить вне Git |
| PUBLIC_ORIGIN | HTTP + Host запроса | Точный внешний HTTPS-origin за reverse proxy |
| COOKIE_SECURE | false | `true` при HTTPS за reverse proxy |

`.env.example` документирует имена. Node автоматически не читает `.env`; задайте переменные средствами оболочки/службы или используйте `node --env-file=.env server/node.mjs`.

Для внешнего доступа нужен reverse proxy с HTTPS, проксированием Host и тайм-аутом минимум 70 секунд (до 3 живых сайтов в batch). Передайте COOKIE_SECURE=true и PUBLIC_ORIGIN=https://ваш-домен при HTTPS; origin используется для защиты от CSRF. Не проксируйте недоверенные identity-заголовки в Worker-адаптер вне платформы Sites. Порт контейнера по умолчанию публикуется только на loopback хоста.

## Docker

```bash
export AUTH_TOKEN='your-long-random-secret'
docker compose up --build -d
```

Контейнер работает под непривилегированным пользователем; база сохраняется в volume `meridian-data`. В образ не входят PDF, Git, браузерные артефакты, `.env` или рабочая БД. Dockerfile выполняет проверку типов, unit/API/runtime-тесты и сборку. Сам контейнерный runtime в этой сессии отдельно не запускался; подтверждён запуск приложения как Node-процесса.

## Hosted demo в Sites

- Существующий project_id сохраняется в `.openai/hosting.json`; повторно Site не создавать.
- `npm run build` выпускает React и `dist/server/index.js` с общим API и встроенными ресурсами.
- D1 binding — `DB`; SQL-миграции хранятся в Git (журнал совместим с Drizzle) и входят в deploy-архив.
- Приватный доступ владельца; не менять audience ради тестирования.
- В этой среде отсутствовал поставляемый с Sites локальный source helper. Git-синхронизация и упаковка выполнены эквивалентными командами с временным credential через stdin, без сохранения его в файлах/исходниках.
- Workers не выполняет Node-сканер и расписание: `capabilities.live=false`, `capabilities.scheduler=false`; API возвращает 503 на недоступные операции. Демо-проверки и остальные операции сохраняются в D1.

Адрес и результат конкретного развёртывания зафиксированы в отчёте тестирования и финальном сообщении. Изменения рабочего портфеля не входят в новый deploy и не сбрасываются при обновлении версии.

## Проверка после установки

1. `GET /api/health` возвращает 200 и версию.
2. Открывается интерфейс, загружается портфель.
3. Добавьте вымышленного мерчанта и выполните демопроверку.
4. Перезагрузите страницу: данные и история должны сохраниться.
5. Откройте отчёт и скачайте CSV.
6. В Node выберите живую проверку своего разрешённого публичного сайта.
7. Включайте расписание только после настройки источников и политики обхода.

## Резервирование и восстановление

Node: делайте согласованную SQLite backup через CLI `.backup` либо при остановленном процессе копируйте основной файл; простое копирование файла при активном WAL не гарантирует полный снимок. Храните копии отдельно от volume и проверяйте восстановление. D1: используйте средства экспорта/восстановления обслуживающей платформы.

Порог JSON-агрегата — 1,8 МБ. При его превышении операция отклоняется до записи с 413 и сохраняет прежние данные. Для продолжительного пилота заранее организуйте архивирование или переход на нормализованную БД; снимки не удаляются молча ради новой записи.

Отдельный промышленный этап: мониторинг, алерты, ротация ключей, корпоративное SSO/RBAC, репликация, юридический срок хранения, регламент восстановления и нагрузочные испытания. Произвольные требования SLA здесь не выдуманы.
